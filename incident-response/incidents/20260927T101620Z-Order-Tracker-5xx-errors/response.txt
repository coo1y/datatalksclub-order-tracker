I treated this as a real incident, not a test. The alert says "resolved" and its value is 0, but it has no test label, and Prometheus still shows about 3 HTTP 500s on `/api/orders/{order_id}`. The bug is still in the code, so the errors will come back whenever someone looks up that order.

**Affected endpoint:** `GET /api/orders/{order_id}`. The PATCH and POST endpoints return their result through the same lookup, so they're exposed to the same failure.

**Root cause:** in `app/main.py`, `order_detail()` worked out the delivery estimate for express orders with `placed_at.replace(day=placed_at.day + 2)`. When an order is placed near the end of a month, that asks for a day that doesn't exist, such as the 33rd, and Python raises `ValueError: day is out of range for month`. The seeded order `express-1002` was created on the last day of the previous month. The logs show "order lookup hit order_id=express-1002" just before the lookup would reach this line, and the 500s line up with those lookups. The logs don't contain a traceback, so that link comes from reading the code, not from a logged error.

**Fix applied:** in `app/main.py`, `order_detail()`, I changed that line to `estimated_at = placed_at + timedelta(days=2)`. `timedelta` was already imported. I checked the old and new expressions for Aug 31: the old one raises the error and the new one gives 2026-09-02. I haven't restarted or redeployed the app, and it still needs a human to review and deploy.

Verdict: Real incident. Express orders placed near month-end crashed the date calculation; fixed in `app/main.py`, waiting for review and redeploy.
